# Dimanche 1/6 : k3s sur la VM 3

k3s est une distribution Kubernetes complète dans un seul binaire. Parfaite pour un nœud unique.

## Le choix réseau : pas d'IP publique, jamais

Le serveur API de Kubernetes (port 6443) n'a **rien** à faire sur Internet. Ici, il n'y est même pas exposable : `lab-vm3` vit sur `10.10.10.13`, derrière le NAT de l'hôte. Ton laptop l'atteint par la route Tailscale `10.10.10.0/24` annoncée par l'hôte Proxmox (étape 4 du samedi).

Pourquoi le *subnet router* sur l'hôte plutôt que Tailscale dans la VM 3 :

- un seul nœud Tailscale à gérer, même quand tu détruis et recrées les VMs chaque week-end ;
- tu atteins aussi `lab-vm1`, `lab-vm2`, les node_exporters et les NodePorts sans rien installer dans les VMs ;
- tu as déjà approuvé la route samedi.

## Ce que fait le rôle `k3s`

1. vérifie que la VM a au moins ~7,5 Go de RAM visibles (8 Go alloués), sinon s'arrête avec un message clair ;
2. écrit `/etc/rancher/k3s/config.yaml` : `node-ip` et `advertise-address` = `10.10.10.13`, `tls-san` (le certificat de l'API inclut l'IP privée), Traefik désactivé (les services sont exposés en NodePort) ;
3. installe k3s **v1.37.2+k3s1** (canal *stable* au 25/11/2026) avec le script officiel `get.k3s.io` et `INSTALL_K3S_VERSION` épinglée. Il ne relance l'installation que si la version change ;
4. attend que le nœud soit `Ready` ;
5. récupère `/etc/rancher/k3s/k3s.yaml` sur ton laptop dans `kubeconfig/homelab.yaml` (ignoré par Git), remplace `127.0.0.1` par `10.10.10.13`, renomme le contexte en `homelab`, droits `0600`.

## Ce que tu fais

```bash
cd ansible
ansible-playbook playbooks/k3s.yml        # ou : make k3s
cd ..
export KUBECONFIG=$PWD/kubeconfig/homelab.yaml
```

**Vérifier**

```bash
kubectl get nodes -o wide
# lab-vm3   Ready   control-plane   ...   v1.37.2+k3s1   10.10.10.13
kubectl get pods -A                       # coredns, local-path-provisioner, metrics-server : Running
kubectl top nodes                         # metrics-server répond
```

## Pièges

- `Unable to connect to the server: dial tcp 10.10.10.13:6443: i/o timeout` : route Tailscale (étape 4). Teste d'abord `ping 10.10.10.13`.
- `x509: certificate is valid for 127.0.0.1, not 10.10.10.13` : le `tls-san` manquait à l'installation. Relance le playbook (il redémarre k3s quand la config change), sinon supprime `/var/lib/rancher/k3s/server/tls/dynamic-cert.json` sur la VM et redémarre k3s.
- Moins de 8 Go sur la VM 3 : Prometheus et Grafana se font tuer (OOMKilled) dès dimanche midi. Le rôle refuse de continuer, et OpenTofu refuse déjà un `memory_mb` < 8192 pour le groupe `k3s_server`.
- Ce kubeconfig est **cluster-admin**. Ne le donne jamais à l'IA (étape 13) et ne le commite pas.
